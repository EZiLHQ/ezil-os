## The problem

`app/package.json`'s `db:apply-0001` script (`node scripts/apply-telemetry-migration.mjs`)
applies exactly one migration file idempotently, because the production database has no
`drizzle.__drizzle_migrations` journal — it was created by some route other than `drizzle-kit
migrate` — so the generic migration runner cannot be used until someone baselines that journal.
`app/drizzle/0002_os_access.sql` (the OS invite allow-list table, `ezil_os_access`) exists and
is additive-only, but there is no `db:apply-0002` counterpart. `docs/CONFIDENCE-MAP.md`'s A1
row measured this directly: "Migration `0002_os_access.sql` was applied to a throwaway
Postgres 17; **the hosted database has never seen it**." Without a safe-apply script matching
the `0001` pattern, applying it to the real hosted database means either hand-running SQL or
reaching for `drizzle-kit migrate`, which is exactly the command `0001`'s script exists to
avoid.

## Acceptance criteria

- `app/scripts/apply-os-access-migration.mjs` (or equivalently named) applies **only**
  `drizzle/0002_os_access.sql`, following `apply-telemetry-migration.mjs`'s five guards:
  refuses without `SUPABASE_DATABASE_URL`; idempotent (exits 0 if `ezil_os_access` already
  exists); reads the SQL from disk rather than embedding it; refuses if the file contains any
  statement affecting existing objects (DROP/TRUNCATE/DELETE/ALTER of a table it did not create
  itself); wraps in one transaction, verifying the table, its RLS flag and its policies before
  committing.
- `app/package.json` gains a `db:apply-0002` script entry, matching `db:apply-0001`'s naming.
- Never prints the connection string or row contents, matching `apply-telemetry-migration.mjs`'s
  existing rule.
- A test (or a documented manual run against a throwaway Postgres) proves both the apply and
  the idempotent re-run.

## Where to look

- `app/scripts/apply-telemetry-migration.mjs:1-40` — the five guards and the pattern this
  issue's script must follow exactly; `EXPECTED_TABLES` at `:34` is the shape to mirror for
  `ezil_os_access`.
- `app/package.json:16` — `"db:apply-0001": "node scripts/apply-telemetry-migration.mjs"`, the
  entry `db:apply-0002` joins.
- `app/drizzle/0002_os_access.sql:1-19` — the migration this script applies; its own header
  comment states it is additive-only and references `src/server/db/schema/os-access.ts` for
  the design rationale.
- `docs/CONFIDENCE-MAP.md`'s A1 row — "the hosted database has never seen it," the measurement
  this issue is opened from.
- `docs/RUNBOOK.md` § "Database migrations — read this before running `drizzle-kit migrate`" —
  why the generic runner is unsafe here (the shared `public` schema holds ~40 tables from an
  older project).

## How to prove it

```
cd app && SUPABASE_DATABASE_URL=<throwaway-postgres> node scripts/apply-os-access-migration.mjs
```
run twice: first run creates `ezil_os_access` with RLS and its policies; second run exits 0
having done nothing (idempotent).
