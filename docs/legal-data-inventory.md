# Hosted EZiL OS: legal data inventory

Review date: **2 October 2026**. Scope: the hosted service at **os.ezil.org**. Companion pages: `/terms` and `/privacy` in `app/src/app/(legal)/`.

This evidence map connects the public legal pages to repository code and documentation. It does not establish live provider settings or operational retention practices. Configuration-dependent behavior is identified below; a capability in code does not prove that every deployment setting or maintenance job is active.

## Diagnostics: exact scope and limits

The source distinguishes three mechanisms. The public Privacy Policy does too.

1. **Structured events:** [shell/ezil/telemetry.js](../shell/ezil/telemetry.js), [schema.ts](../app/src/server/telemetry/schema.ts), [types.ts](../app/src/server/telemetry/types.ts), [ingest.ts](../app/src/server/telemetry/ingest.ts), and [telemetry database schema](../app/src/server/db/schema/telemetry.ts). Nine classes: `boot_phase`, `boot_summary`, `boot_stall`, `crash`, `window_error`, `api_failure`, `display_failure`, `worker_exception`, `contract_violation`. Outcomes can be `ok`, `error`, or `skipped`; **“only failures ever” is too strong** because [worker selectTelemetryWorthy](../worker/src/telemetry.ts) includes boot summaries.
2. **Fields and linkage:** event UUID, schema version, class, source, fingerprint, pseudonymous user hash, site/code, outcome, redacted detail, optional duration/correlation/computer IDs and allowlisted attributes, occurred/received timestamps. Attributes include short stack head, app ID, status/retryable, display observation, phase count and duration. Raw event rows, per-user hourly counts, and error-type summaries are separate tables. The user hash is unsalted 32-bit FNV-1a (`u_…`), recomputable from known account IDs, with collision risk. It is **pseudonymization, not anonymization**. Worker/container imports use the sentinel value described in `types.ts`, not a newly asserted per-user identity.
3. **Separate operational logs:** [worker/src/observability.ts](../worker/src/observability.ts) includes sandbox ID and user pseudonym in lifecycle logs; [index.ts](../worker/src/index.ts) has failure logs that include `relPath`; [computer-store.ts](../app/src/server/api/routers/computer-store.ts) logs teardown errors with computer ID and raw error message. Hosting/authentication/relay providers process IP and request/connection metadata. Their enabled logs and retention were not verified. **Do not extend the structured telemetry redaction promises to all logs or all hosted processing.**

[sanitize.ts](../app/src/server/telemetry/sanitize.ts), [worker observability sanitizer](../worker/src/observability.ts), and the shell redactor scrub error descriptions and truncate detail. Strict top-level schema plus attribute allowlists reject/drop unexpected fields. These are best-effort data minimization, not a proof of zero personal information: space-containing unquoted paths can leave suffix text; arbitrary allowed strings are not a formal non-disclosure guarantee. Existing [telemetry.md](telemetry.md) describes the residual path case but has older “never” and “no identities” phrasing that must not become a blanket legal promise.

The admin review page is restricted by a configured email allowlist, default-deny: [admin.ts](../app/src/server/telemetry/admin.ts), [admin/telemetry/page.tsx](../app/src/app/admin/telemetry/page.tsx), [0001 migration](../app/drizzle/0001_telemetry.sql). Service/database administrators can access data; RLS for users is not zero-knowledge encryption or an inability for EZiL to read hosted files.

The shell sends diagnostics only with a hosted authenticated boot context; there is no settings toggle. Blocking browser submissions affects that producer, not worker/container diagnostics or infrastructure logs. See [http-handler.ts](../app/src/server/telemetry/http-handler.ts), [shell telemetry](../shell/ezil/telemetry.js), [worker telemetry](../worker/src/telemetry.ts).

## Local/native and roadmap distinctions

- [README](../README.md), [LOCAL-MODE](LOCAL-MODE.md), [local/config.ts](../local/src/config.ts), [local container run spec](../local/src/container/run-spec.ts): local Docker mode runs without hosted authentication/providers; configured local workspace mounts remain local. Internet access to chosen destinations is still possible.
- [macos-electron/workspaces.cjs](../macos-electron/src/workspaces.cjs), [browser.cjs](../macos-electron/src/browser.cjs), [desktop-state.cjs](../macos-electron/src/desktop-state.cjs), [NATIVE-MAC](NATIVE-MAC.md): native managed workspace files, persistent browser profiles, editor data and desktop state live on the Mac. Native commands/extensions execute as the Mac user. App removal is not necessarily local data erasure. These facts must not be used to imply hosted profiles are also persistent.
- [ROADMAP](../ROADMAP.md): local-to-cloud workspace synchronization and local agents are future/research work. Old invite-only/domain-migration language conflicts with current [trpc.ts](../app/src/server/api/trpc.ts) and login actions; the legal pages use current public Google signup at os.ezil.org.
- [app-store.js](../shell/ezil/apps/app-store.js): Reticle is marked planned and not installable. Neither Reticle nor its possible model providers are described as current recipients. App manifest/policy modules define validation capabilities, not proof of deployed marketplace installation or permission grants.
- The pages explain notice for material future changes without presenting roadmap items as available functionality.

## Maintenance responsibilities

1. Keep the public operator and monitored contact details current. Review material policy changes against applicable law.
2. Maintain provider, hosting-region, relay, and international-transfer information. Repository configuration alone cannot verify provider contracts or executed transfer safeguards; the public pages avoid claiming a particular unverified mechanism.
3. Handle access, export, and erasure requests across Supabase Auth, computer and invitation records, R2 workspace prefixes, diagnostics, logs, and backups. Database account deletion alone does not establish complete workspace erasure.
4. Monitor production cleanup execution, diagnostic spool backlog, log and backup retention, and any retention schedules managed outside this repository.
5. Revisit the policy when OAuth fields, integrations, support services, analytics, or persistence behavior change. Planned features must not be described as active recipients or functionality.
