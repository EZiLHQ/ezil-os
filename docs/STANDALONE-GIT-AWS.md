# Standalone Git on the owned AWS computer

The commit/push update starts from staging `5127d85f71af309dc7c47537a6be276a7de1eb9d`. Deployment and host/AMI custody remain with the existing staging release owner.

Standalone repository execution uses a closed operation over the existing gw1 tunnel and signed agent socket. Commit/push support extends that operation with verified author metadata and refresh-only authorization. It does not add a generic command, executable, root path, download URL, or script field.

1. OS verifies computer ownership, obtains the shared OAuth identity's exact standalone v2 grant, and mints Code using the selected computer's normal provider path. It re-reads the placement after minting. Public github.com opens retain their existing provider restriction.
2. Worker verifies the app's body-bound v2 claims. An AWS request must carry the standalone packet. The tunnel's computer, generation and lease epoch must match at admission and on every status poll; an absent/fenced/stale tunnel is refused without a Cloudflare fallback.
3. Worker sends `{v:1, jobId, repositoryId, privatePacket, timeoutMs}` with optional validated outer `gitAuthor` and `refreshOnly` fields to `POST /__ezil/control/standalone-repo-open/<sha256(body)>`. gw1 binds the digest path and epoch. Edge compares the exact bounded Content-Length body before strict JSON parsing, then signs the same narrow request to the host agent.
4. Agent admits at most one operation on a running desktop, refusing stop/export/restart quarantine. Job and grant remain in memory, never on the data volume or a host request file. A repeated job ID reports that job; its token-free result expires after ten minutes. Unknown outcome quarantines further opens rather than deleting locks or user files.
5. Host executes only the reviewed public bootstrap and pinned Node CLI inside the existing runc desktop. Public bootstrap input contains no credential. The grant reaches the fixed in-container FD adapter on anonymous stdin and the reviewed supervisor/CLI through anonymous FD 3. The grant is absent from argv, environment, persistent workspace files and logs. The CLI retains its short-lived credential only in a protected repository-bound file under the container's ephemeral `/run`, outside the workspace and checkpoints. The supervisor enforces the deadline, reaps descendants and preserves uncertain state.
6. CLI opens `/workspace/projects/<deterministic UUID>/<repository name>`; Code opens only its parent wrapper. A successful, validated reopen of an older `repository` child migrates that directory to the repository name without changing the index, local commits or files. Collisions, symlinks and unexpected wrapper contents refuse. The UUID continues to isolate repositories, and the checkout's editor/agent configuration stays below the workspace root. Host matches the exact CLI output identity, provider repository ID, ref and folder. Worker binds the result to its one random job ID and validates the exact requested wrapper; it does not claim a second CLI identity attestation. The OAuth subject is not translated into a Works identity.

The signed OS request may separately carry `gitAuthor: {name, email}` from the verified sign-in and `refreshOnly: true`. Neither field changes the gateway's exact v2 grant packet. They are added only to the private CLI bootstrap on FD 3 together with the OS's constant `gitAccess: true`, so push authorization is installed even when no verified author email is available. The author never appears in the command line. Renewal uses `--repo-refresh`: it refuses a missing checkout, creates no directories, and never migrates paths while Code may have unsaved files open. A private per-wrapper lock spans destination selection, CLI execution and migration so simultaneous opens cannot recreate the legacy child. These fields require the matching public CLI release. The Worker and host now pin the published `0.3.0-standalone.20261115.1` artifact and its exact source, archive and executable digests.

Legacy migration refuses checkouts with any explicit `core.worktree` setting, including included local configuration: that setting may anchor Git to the old path. The checkout, configuration and files remain at their original location; the operation does not rewrite a user's Git configuration to force migration.

These protocol changes require a qualified host-agent rollout: an older host rejects the new request fields. An app/Worker-only rollout cannot update host validation or the installed supervisor. Desktop image bytes need no change if the selected desktop already provides Python, Node >=22 and Git; otherwise the public bootstrap fails closed and the release owner must qualify that concrete image requirement. This source branch launches no AMI, image, host or lifecycle operation.

Admission performs only bounded readiness reads (mountpoint and runc state each <=500ms) while the lifecycle lock is held. Clone/bootstrap run outside that lock. Runtime enablement remains off by default in both app and Worker until the new host-agent capability is qualified. This feature adds no database migration. The release owner must qualify current registry capacity before adding a matched AMI.

## Qualification and runtime custody

Both app and Worker require AWS_STANDALONE_REPO_OPEN_ENABLED explicitly enabled; Worker also requires its existing AWS routing gate. It stays off during app/Worker rollout and host AMI qualification. Runtime custody and the original user's resource remain with the existing staging release owner.

The AMI source archive is the complete committed infra/host-agent tree. The current installer copies bin and lib recursively (cp -a), including standalone_git_assets/{stage.py,supervise.py,pin.json}. An offline smoke test executes that exact copy line into a disposable install root, imports from an unrelated cwd, and compares helper/source hashes. It invokes no image build or external service.

Offline receipts prove the actual anonymous-pipe FD adapter and reviewed supervisor separately from the mocked runc exec call shape. The release owner must still observe the real runc stdin/FD3 boundary, Python/Node>=22/Git availability, bounded cancellation/reaping, exact wrapper and dirty reuse on the capped staging canary before enabling the capability. Failure stays closed; no alternate interpreter, arbitrary URL, unpinned executable or generic exec endpoint is accepted.

The host admission marker contains only its random job ID and remains after agent restart or unconfirmed cleanup. Recovery is a custody operation: establish that the owned in-container supervisor/descendants are gone and inspect CLI recovery state before clearing a marker. This feature never clears CLI locks, resets a checkout, deletes user files, or performs lifecycle recovery automatically.

## Signed-in acceptance

Use a fresh isolated browser context and an existing test identity. Open `/login?returnUrl=%2Fcomputers`, choose **Continue with EZiL ID**, and finish the normal sign-in. The email/password fallback does not retain the verified Auth0 identity required for standalone Git grants. The computers page lists owned computers without starting one; select the approved test computer explicitly after the release custodian gives the runtime handoff.

First verify the signed-in OS identity and selected computer through the read-only `/api/shell/session` route. Open the fixture repository in Code and check its readable child folder and repo-local author. Author attribution comes from the verified sign-in when configuration is missing; existing user configuration remains intact. This does not configure cryptographic Git commit signing.

Record the existing index, local commits and dirty-file state before the test. Edit one dedicated acceptance file in Code, commit only that file, and push normally without resetting or including unrelated staged changes. Independently compare the remote ref with the new commit SHA and inspect both author and committer. Keep Code active beyond the original grant lifetime, then edit, commit and push a second change to prove credential renewal. Reopening must preserve the original staged, unstaged and untracked state and existing local commits.

A repository collaborator grant is permission evidence. Acceptance for a particular user still requires that user's normal sign-in and actual push; a test under another identity cannot establish it. Keep credentials and browser session data out of acceptance receipts.
