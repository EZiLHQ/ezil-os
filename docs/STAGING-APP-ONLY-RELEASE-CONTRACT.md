# Staging whole-app folder release: proposed custody contract

**Status: design for independent review; not an implemented or authorized execution procedure.** The implemented operator and its executable plan, including a reviewed deviation (it reuses `install-host.sh` rather than a new web-only installer), are in `STAGING-APP-ONLY-RELEASE-PLAN.md`. No cloud operation is performed by this document. The existing release scheduler is the only staging cloud writer. This proposal does not replace its lease, admission, recovery gates or the current release plan.

## Why current entry points are insufficient

`deploy/aws/os-staging/install-host.sh` extracts runtime files, stops six timer/service pairs, renders the environment, replaces `compose.env`, force-recreates Compose services, installs unit files and enables timers. A mismatch can leave timers stopped; log snapshots are pruned. Generic rollback requires the prior image, runtime and checksum; it does not preserve timer states automatically.

`deploy/aws/mum/rebase_release.py` `apply-app` uses that installer, requires `rollout.app.gitSha == bake.agentCommit`, and journals a pending and completed operation. The frozen plan pins 7fcc; substituting the candidate invalidates its pins. `ledger-adopt-app` records an already-running forward descendant with matching tuple/registry. It does **not** fence a preceding installation and refuses a return to 7fcc. Its dry-run path still performs a live, read-only SSM readback and must stay under scheduler custody. Reinstalling the prior image with the generic installer re-renders from current secrets; it does not restore prior Secrets Manager values or database schema. Direct JavaScript overwrite loses source identity and restart persistence. Separately, `deploy.sh install` and `install-verified` can send `AWS-RunShellScript` without checking this ledger or lease; their host `deploy.lock` is process-scoped and vanishes on crash. A ledger-only pending marker cannot fence them. These are not currently a custody-preserving app-only deployment of this candidate.

## Proposed minimal integration (not implemented)

The payload is one **whole immutable app image** built from candidate source. An app-only operator must be added to the existing ledger and every schema consumer before use; older tooling must fail closed on the new pending operation. It must not call the generic runtime installer or alter production. The operator, pinned installer and scheduler handoff need independent code review and fake-host/fake-ledger tests.

### Immutable plan and artifact

1. Review exact source commit, parent, Git tree, source archive digest, shell digest, tests, staging target and public-configuration fingerprint. Obtain immutable remote source; a local worktree alone is not release custody.
2. Build from a clean export with staging-only public configuration. Verify source receipt, image revision, architecture, image/config ID, archive SHA-256 and rendered config identity. Publish to a new non-overwritable staging-only object version and pin that version, digest and receipt. No candidate image has been built or uploaded yet.
3. Pin rollback to owner-verified 7fcc archive/version, original image ID and marker/runtime digests. Reverify bytes and that the old app accepts the unchanged lifecycle tuple, registry, public configuration and kill-switch state. Refuse if an input is unavailable.

### Admission and ledger

Before enabling this design, inventory every principal, session, document and host path able to install or change the staging app, including generic SSM root commands, old installer scripts and direct host access. Drain already submitted commands and prove every normal mutation path is restricted to the fixed, reviewed, pending-aware operation or is otherwise unavoidably fenced. A marker in a file, a cooperative client check, or a process-scoped host lock is insufficient if a generic root command can bypass it. Document how break-glass access is excluded or detected, and fail closed if this inventory or enforcement is incomplete. This enforcement does not exist in the offline model.

1. Scheduler confirms that r9/recovery/CloudTrail observation and expiry permit an app mutation. Do not assume the observation survives a switch; schedule required new evidence and replan when the ledger advances. Maintain KS1 and exact lifecycle tuple/registry. No schema, IAM, AMI, Worker or computer workspace mutation is part of this switch.
2. Use the existing single staging lease; do not displace an owner. Under the established app-secret lock verify live app SHA and image ID, tuple, registry hash, secret version, target host, timer state and expected latest completed ledger generation; refuse drift or another pending operation. Bounded command time and a durable pending fence must survive a lost response or approaching lease expiry. This requires implementation, not an inference from the lease.
3. Before any image/container/config mutation, atomically append and fsync a newly defined **pending app-swap** under lock. Pin plan digest, generation, operation ID, before/expected app SHA and image ID, immutable image/receipt/rollback versions and digests, unchanged tuple/registry, target, installer digest, lease identity and operation journal. All consumers must fence other plans. If persistence or comparisons fail, do not submit.
4. Bind one SSM command to the generation and exact payload digest. Lost response, timeout, reboot, lease expiry or partial installation is **unknown**, not permission to resend. The current `rebase_ssm.run` changes a failed journal to uploading on a later apply and can resend; the new one-shot operation must not inherit that retry path. Retain pending ledger, command ID and journal; inspect the command and actual host, then reconcile only that operation. Do not automatically retry, roll back or release the fence while uncertain. A terminal SSM status alone does not prove spawned processes or Docker-daemon work stopped. A failure may be recorded as aborted only after proving host-side mutation activity is quiescent and the complete before-state remains stable; otherwise retain the pending fence. A new submission requires a new reviewed operation and generation.

### Host behavior and atomicity

A new reviewed installer may load the pinned image by digest, verify image ID, revision and architecture, and replace **only** the `web` container using already-installed Compose and Caddy configuration. It must retrieve each exact pinned object version and verify its digest, then pre-validate the image archive manifest and all tags against an approved unique candidate tag before `docker load`: loading an archive can move an existing tag before post-load inspection. The existing generic installer reads mutable S3 keys and does not provide these guarantees. The new path must first prove Compose/env files match expected nonsecret fingerprints and preserve their exact bytes and permissions. Do not render or replace app secrets, Caddy, cron units, host scripts, Worker or other services, and never overwrite the previous image tag.

Retain a durable before/after journal and use same-filesystem atomic replacement plus file and directory fsync for any changed image selector. The file update and Docker recreation are **not one atomic operation**. Reconcile a crash by inspecting selector, container image ID and app readback against the journal; never guess. A web restart causes brief unavailability and may disconnect browser sessions. It must not restart a user computer or mutate its persistent volume.

Capture the six timers' actual enablement/activity and in-flight work. The owner must decide from current evidence whether leaving them running through web restart is safe or scoped quiesce is required; their requests can fail during downtime. If quiesced, restore only previously active/enabled states and verify each, including after failure. Do not claim no timer or work was affected until observed. This requires new implementation and tests; it is not today's generic installer.

### Completion, failure and rollback

1. Under the same pending generation, verify running image ID and app `gitSha`, KS1, full tuple/registry, unchanged non-web runtime, expected timers, staging health and served bundle digest. Complete the ledger from these technical readbacks while KS1 remains closed; do not require a signed-in computer to complete the pending operation.
2. After technical readbacks pass, append a completed app-swap entry with observed new SHA and unchanged tuple/registry. Record source, image ID, object versions/digests, command and health receipts. Tell the scheduler the new generation; maintain KS1 while it replans and collects required recovery observation. Only after the release owner reopens admission, test signed-in folder open, copied URL/new tab, refresh, Forget/reconnect and workspace persistence/restart. Test cache revalidation separately: `Cache-Control: public, max-age=0` alone does not prove intermediaries or open tabs refreshed. Product acceptance remains separate from ledger completion.
3. After a failure with pending written, do not use `ledger-adopt-app` or a raw legacy install to imply completion. Inspect command, selector, container and timers first. A reviewed reconcile must distinguish exactly before, exactly expected and any third state; retain the fence on uncertainty and restore gate/timer state intentionally.
4. Return to 7fcc **after** app-swap completion requires a separate reviewed, journaled **pending app-restore** whose approved expected SHA is exactly prior 7fcc. Restore the pinned old image/selector, preserve current tuple/registry and append its own completion only after readback. Existing `ledger-adopt-app` forbids reverse adoption; no such app-restore operation exists today. If tuple/registry changed, re-evaluate compatibility and draft a new plan; do not restore runtime, secret or SQL blindly. A forward-descendant revert image requires a separate build and review and is not the verified 7fcc artifact.

## Offline verification needed before implementation can be proposed for release

- Wrong candidate/rollback source, receipt, archive, image ID or object version rejects before submission, with no timer, file, container or ledger mutation. Simulate a substituted S3 version and an archive containing a previously used tag: both must fail before Docker load can move that tag.
- Pending persistence failure prevents send. Test that a simulated stale legacy install and every inventoried bypass are denied while pending, and separately verify the real IAM/document/host guard before live use; a cooperative fake alone is not proof of enforcement. Test lease expiry, lost SSM responses, delayed success, host reboot and concurrent lease attempts. A failed or ambiguous journal cannot follow the current rebase SSM automatic resend path; test no duplicate sends, including retries after terminal failure.
- Crash after each image load, selector rename, container stop/start, health check and ledger append; reconcile sees before, expected or unknown without duplicate submission.
- Failures preserve or restore exact selector bytes, permissions, Caddy/runtime, secret, computer data and each recorded timer state. Test an in-flight timer/service, failed restart and terminal SSM failure with continuing host/Docker activity: it must remain fenced until quiescent and stable. Never automatically roll back an ambiguous command.
- Test app-restore to the reviewed old SHA as a separate operation, including incompatible tuple, registry change, corrupt/unavailable rollback, stale source, duplicate and interrupted restore. Demonstrate existing `ledger-adopt-app` refuses reverse adoption.
- Demonstrate app SHA and shell digest through the app server, cache revalidation, Worker bridge compatibility and signed-in folder flows. Assert prior plans become stale when the ledger changes; record the renewed recovery/CloudTrail observation and scheduler handoff.

Existing fake-host and fake-ledger tests characterize today's code; their success does not implement or approve this proposal. The owner and independent reviewer must decide whether completing this work is faster than a freshly reviewed full rollout under the existing supported path.
