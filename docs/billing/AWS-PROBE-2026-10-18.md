# AWS capability probe for billing v2 (2026-10-18)

This is a **real** AWS measurement, tagged and cleaned up afterwards. It used `infra/app-computers/probe/billing_v2_aws_probe.py` (run `bv2-20261018T191106Z-a6e0d7`; raw results in `evidence/aws-probe-bv2-20261018T191106Z-a6e0d7.json`).

**What it is.** A direct EC2 measurement of the primitives billing v2 and the Mumbai pool / US failover design depend on.

**What it is not.**
- It is **not** a product lifecycle end-to-end run. That would need the app's lifecycle-authority endpoint on a deployment backed by the production database, which is out of scope for this sandbox request.
- The guest's "boot" and "data ready" are init-script markers on the serial console. They are **not** desktop, editor or tunnel readiness.
- Click-to-interactive latency for the product is still unmeasured.

**How it was run.**
- Identity: AWS SSO `AdministratorAccess` session of the founder (re-authenticated in-session). No root, and not the expired default profile.
- Resources: default VPC, no public IPs, IMDSv2 required.
- Disks: encrypted gp3 with each region's default EBS key. No new IAM role, KMS key or security group.
- Each instance had a self-terminate backstop at 40 minutes.
- Cost: an estimated **$0.07** for this run, and about $0.15–0.20 across all three runs, against a $10 cap.
- Cleanup was verified by tag sweep: 0 instances, 0 volumes and 0 snapshots left in ap-south-1 and us-east-1.

**What this means for the design.**
- **Warm start.** Attaching and mounting a user's disk on a pre-booted clean host takes about 2 s. The warm-ready target of under 5 s is plausible for the disk step. The remaining product steps (tunnel, desktop, editor) are unmeasured and must be measured before any claim is made.
- **Cold start.** A cold start is about 12 s to the guest init script, before any product services. A size change costs a full stop/start: about 20–45 s to stop, and about 10 s from start until the disk is mounted.
- **Failover.**
  - Cross-region recovery of a small disk took under 2 minutes. It loses all writes after the snapshot point, and RTO grows with the amount of changed data.
  - A regular replicated snapshot cadence sets the real RPO.
  - The writer must be fenced (stopped, plus a generation bump) before the replica is mounted, so two writers never run.
  - Nothing should fail back automatically.
- **Probe bug found and fixed.** After a stop/start, Nitro may enumerate the root disk as `nvme1n1`. An earlier run's watcher picked the first `nvme[1-9]n1` and mounted the wrong disk, which showed up as "marker not preserved" (run 2 evidence). That run's cross-region restore of the same user disk carried the original marker, so the user data had been intact all along. The host agent must identify the data disk by volume serial, never by device name, as LIFECYCLE.md already requires.
