# Standalone Git URL open — OS slice

Implementation began from live `os-staging` `/api/health` SHA `74e26bfad79a842bda16d166ab35b86696818159` (checked 2026-11-10). The source review branch is based on current staging `d6e37771be35783b612a16031f09a087d62b39eb` and carries the generated bundle from both shell changes so PR #331 can run normal CI; this source base does not choose a deployment source. This branch owns only the OS app, Worker, and Code URL consumer. The existing OS release owner `40003c71` retains staging and deployment custody.

The direct URL route accepts canonical `https://github.ezil.work/<namespace>/<repo>.git`. After the selected computer's owner/provider checks, it obtains this session's verified EZiL ID token and asks `POST https://github.ezil.work/v2/git/grant` for write, retrying read only after a 403. The gateway's exact v2 packet supplies the actual Cloudflare repository ID, canonical URL, ref, issuer/subject, scope, opaque Basic credential, and expiry. OS derives a separate stable checkout UUID from the URL. Grant and session continuity are checked before Code wakes; the signed Worker route passes the packet to the bundled CLI on fd 3. Code opens the safe parent wrapper, with the checkout in `repository/`. No direct URL authorization uses a Works API or project binding.

The app and Worker accept the native Artifacts `art_v1_<40hex>?expires=<epoch>` credential as opaque packet data while retaining token length, colon, whitespace, and control-character checks. The published CLI `.0` archive is incompatible with that credential and must not be installed. `worker/src/repo-open-runtime.ts` carries the `.1` candidate URL, archive SHA-256 `a8b47e8ff292afbfbf17e24be0a12f335fc2169ac9f50d055c8e546939f8a2b5`, entry SHA-256 `3b88146b48d73637274f9e4d42ed139cbc2d9b0b93f3bad6236fd23a66c919c4`, and source commit `141d75e192f468bbdeda8cc8cafdf2feebc87e3a`. Root has not yet confirmed the public download bytes. `STANDALONE_CLI_RELEASE_READY` remains `false`, so the Worker refuses a private open before any runtime exec.

Image 1.0.39 permits an ephemeral `/run/ezil` bootstrap in principle: the image already uses a root-only `/run/ezil/bin` grant helper, and the system snapshot's roots exclude `/run`. There is no structural image bake requirement. The container's Node **major version still needs verification** before this Node 22+ bundle can be used. The implemented Worker install is:

1. After the computer's running check, fetch the **public reviewed archive** from its source-pinned GitHub release URL without any OAuth or Git credential. The download is limited to 2 MiB and the whole helper to 18 seconds; HTTPS redirects are limited to GitHub release asset hosts. The helper checks archive SHA-256, exact `dist/ezil.js` SHA-256, source commit, package version, members and size; unsafe members and links fail.
2. Check `node --version` is at least 22. Under a two-second lock, require real root-owned `/run/ezil` and `/run/ezil/bin` directories with mode 0700. Write the CLI and generated, hash-checked `supervise.py` to temporary files in that directory, atomically rename with mode 0500, and verify exact `ezil --version` output. Pin metadata is nonsecret and stays under `/run`.
3. Every private open calls the bootstrap again. It checks installed CLI and supervisor hashes, owner/mode, metadata, and version before the CLI receives a grant. The Worker also gives its expected CLI hash and version to the supervisor. The bootstrap's elapsed time is subtracted from the open deadline and the grant's remaining lifetime is checked again. On failure the Worker returns `repo_open_git_missing` or a deadline error, without calling the CLI. Nothing enters `/opt`, `/usr`, `/etc`, a persisted workspace, or the image manifest.

The staging workflow can deploy app/Worker changes with `image_changed=false` and `--containers-rollout none` only when its last successful deployment image receipt is valid and the `IMAGE_INPUTS` comparison is unchanged. Otherwise it takes the normal tested and attested image path. A missing public artifact, Node below 22, or failed runtime checks is a release blocker; do not bypass the image receipt or attestation to force the fast path.
